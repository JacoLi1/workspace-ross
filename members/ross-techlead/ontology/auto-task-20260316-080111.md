## 3. Expected Strengths of Current Design

1. **Simplicity of Deployment**  
   Single artifact (`kitchensim-engine.jar`) is easy to ship and run. No versioning conflicts between modules.

2. **Performance via Direct Calls**  
   No interface indirection overhead; all method calls are direct (vtable vs virtual interface). For a simulation targeting 60Hz, this matters.

3. **Tight Integration**  
   Device logic can directly manipulate entity storage without abstraction layers. Ontology queries can be inlined, avoiding service lookups.

4. **Easier Debugging**  
   One stack trace, one debugger session, no classloader issues. Breakpoints work across all code.

## 4. Anticipated Weaknesses & Coupling Risks

### 4.1 High Cyclic Dependency Likelihood

**Problem**: Device creation needs ontology type info → `DeviceManager` calls `OntologyParser`; but ontology loading needs `ResourceManager`; `ResourceManager` may need logging from `SimulationEngine`. These form cycles.

**Impact**: Cyclic dependencies make modular extraction impossible without major refactoring. Compilers may allow it via split packages, but it's a ticking time bomb.

### 4.2 Mixed Abstraction Levels

**Problem**: The `SimulationEngine` class likely contains:
- High-level: time loop, event scheduling
- Mid-level: device update ordering
- Low-level: OpenGL context setup, texture binding

**Impact**: Changes to rendering (low-level) force recompilation of core engine. Violates Stable Abstractions Principle.

### 4.3 Global State proliferation

**Problem**: Quick-and-dirty implementation likely uses:
```java
public class SimulationEngine {
    public static DeviceManager devices;  // singleton
    public static EntityManager entities; // singleton
}
```
**Impact**: Modules become** untestable in isolation**; any test must initialize the entire world.

### 4.4 Ontology as Runtime Dependency

**Problem**: If `DeviceManager` directly imports `OntologyParser` and calls `owlClass.getSubClasses()`, then ontology becomes a hard dependency of the domain layer.

**Impact**: Cannot run simulation without OWLAPI and ontologies present, even for unit tests of device temperature models.

### 4.5 Visualization Tied to Simulation State

**Problem**: `Renderer` likely receives `SimulationEngine` reference and queries device positions directly each frame.

**Impact**: Rendering thread blocks on simulation lock; cannot decouple for multi-threaded pipeline.

## 5. Refactoring Recommendations

### 5.1 First 72 Hours: Stabilize & Characterize

1. **Run static dependency analysis**  
   Use `jdeps --recursive simulation-engine.jar` to generate actual import graph. Compare with expected architecture.

2. **Create characterization tests**  
   Before any refactor, write tests that capture current (monolithic) behavior:
   - `EngineSmokeTest`: run 1000 ticks, verify entity count unchanged
   - `DeviceStateTest`: create stove, set temp, verify after N ticks
   - `OntologyLoadTest`: load sample OWL, ensure no exception
   These are **golden tests**—after refactor, they must still pass.

3. **Identify hot spots**  
   Profile a 60-second simulation run. Find which classes allocate most memory or consume CPU. These are refactor priorities.

---

### 5.2 Extraction Order (Minimize Breakage)

**Step 1: `resources` and `eventbus`**  
- Extract `ResourceManager` to standalone module with no dependencies.
- Extract `EventBus` (publish/subscribe) to `dispatcher` module.
- **Why first**: They are pure utilities with lowest coupling. Success builds confidence.

**Step 2: `core.engine` Time System**  
- Extract `Scheduler`, `TimeStep`, `EngineLoop` to `core`.
- `SimulationEngine` becomes a thin orchestrator that delegates to `FixedStepScheduler`.
- **Validation**: Engine runs 1000 ticks in isolation without other modules.

**Step 3: `entities`**  
- Extract component storage, entity lifecycle.
- Replace global maps with `EntityManager` instance injected via constructor.
- **Breakage risk**: High. All device and renderer code must be updated to use `EntityManager` instead of direct static access.

**Step 4: `devices`**  
- Now that `entities` and `core` are standalone, extract all device classes.
- Introduce `DeviceFactory` interface; current implementation uses `OntologyBridge` (which depends on `resources`). This is acceptable because `devices` can depend on `resources` (Layer 2 → Layer 0 OK).
- **Validation**: Device unit tests run without pulling in visualization or ontology.

**Step 5: `visualization`**  
- Extract renderer; now it depends only on `entities` (for transforms) and `resources` (for meshes).
- Hook to `dispatcher` tick events.
- **Risk**: OpenGL context must be created on main thread on some platforms. Keep this code isolated in visualization module.

**Step 6: `ontology`**  
- Finally, extract OWL parsing. This module depends on `resources` (to load OWL files) and has no runtime impact on core simulation if we keep it as a bootstrap-time operation.
- **Validation**: Load kitchen.owl, query `Stove` hierarchy, ensure matches expected.

---

### 5.3 Interface Design Principles

- **Dependency Inversion**: High-level `DeviceManager` should depend on abstraction `DeviceFactory`, not concrete `OntologyDeviceFactory`. But this can be added later—first extract concrete modules, then introduce interfaces.
- **Constructor Injection**: No `new` or `getInstance()` inside business logic. All dependencies passed from top-level composition root (`SimulationEngine` main).
- **Immutable Data**: `TimeStep`, `DeviceState` should be immutable value objects. Prevent accidental sharing.

## 6. Open Questions (Design Decisions Needing Clarification)

1. **Should Ontology be a compile-time or runtime dependency?**  
   If we compile OWL to Java code (code generation), `ontology` module disappears at runtime. That would be ideal for modularity. But requires build-time tooling. Decision pending.

2. **How fine-grained should Entity Components be?**  
   `TransformComponent` (position+rotation) is obvious. Should `TemperatureComponent` be separate from `PowerComponent`? Or combined as `DeviceStateComponent`? This affects module boundaries: if `TemperatureComponent` is used by both devices and physics, then `devices` and `physics` (if exists) both depend on `entities`—acceptable.

3. **EventBus threading model**  
   Should event delivery be synchronous (publisher blocks until all subscribers finish) or asynchronous (queue to main thread)? Synchronous simpler but risks cascading delays. Asynchronous requires thread-safe event objects. Need to decide early.

4. **Resource loading**  
   Should `ResourceManager` support hot-reloading (watch file changes)? If yes, adds complexity (file watcher threads, cache invalidation). Likely out of scope for v1.0—keep it simple: load once at startup.

5. **Determinism requirements**  
   Does KitchenSim require deterministic simulation across platforms (same seed → identical results)? If yes, must avoid non-deterministic collections (HashMap iteration order), floating-point nondeterminism (x86 vs ARM), and threading races. This constrains the entire design. Assumption: **Yes, determinism is required** for reproducible research/agent training.
